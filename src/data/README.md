# `src/data` — local data layer

Implements `docs/08-database-schema.md` and the repositories of `docs/09-interfaces-and-integrations.md`
section 1.5. Spec: `odd/tasks/phase-1-manual-tracker.md` T2 (S6, S7, S10). `src/core` never imports from here.

## Layout

| Path | What |
| --- | --- |
| `schema.ts` | Drizzle schema of `app.db` (all docs/08 section 4 tables, indexes of section 6). No column holds an API key. |
| `migrations/` | SQL generated by `drizzle-kit` and **committed**; `migrations.js` bundles the SQL for the app. |
| `database.ts` | `initializeDatabase(db)`: foreign keys on, then every pending migration in one transaction. Throws a typed `DataError`. |
| `localDate.ts` | `deriveMealTime`: the one place that derives a meal's UTC timestamp and local date. |
| `repositories/` | One repository per aggregate; `createRepositories({ db, catalog })`. Screens never run SQL. |
| `catalog/sqliteCatalogDb.ts` | Core's `CatalogDb` port over any handle with `getAllAsync`. |
| `expo/` | App-only wiring: open `app.db`, install and open `catalog.db`. Not imported by tests. |
| `testing/` | Test-only helpers on `node:sqlite`. Never import from app code. |

## Changing the schema

1. Edit `schema.ts`.
2. `npm run db:generate` (`drizzle-kit generate`, config in `drizzle.config.ts`, `driver: 'expo'`). Commit the new
   folder under `migrations/` **and** the updated `migrations.js`.
3. Migrations are forward-only. Never edit a migration that has shipped.

`babel.config.js` (`babel-plugin-inline-import` for `.sql`) and `metro.config.js` (`sql` in `sourceExts`) are what let
the app bundle the SQL files; Jest uses the same Babel config.

## One code path on Node and on the device

Drizzle 1.0 has two synchronous SQLite drivers with the same API: `drizzle-orm/expo-sqlite` (app) and
`drizzle-orm/node-sqlite` (tests, on Node's built-in `node:sqlite`). Both give a `SQLiteAsyncDatabase<'sync'>`, which is
the `AppDatabase` type. The schema, migrations and repositories are identical; only the line that opens the database
differs (`expo/appDatabase.ts` vs `testing/nodeDatabase.ts`). Consequence: **transaction callbacks are synchronous**
(use `.run()`, `.all()`, `.get()` inside them); awaiting happens outside, before the transaction starts.

## Shipping `catalog.db`

`catalog.db` is built by `npm run catalog:build` into `catalog-build/` (git-ignored, about 6 MB) and bundled as a Metro
asset by `expo/catalogAsset.ts` (`require('../../../catalog-build/catalog.db')`; Metro's default `assetExts` already
include `db`). So:

- **Run `npm run catalog:build` before `expo start`, `expo run:android`, Gradle or `expo export`.** Without the file the
  bundle fails to resolve the require, on purpose.
- The release workflow (docs/06 section 7) must run the same step before the Gradle build. It only downloads CC0 USDA
  files, so it costs nothing, and the downloads are cached in `catalog-build/downloads/`.
- At startup, `expo/catalogDatabase.ts` copies the asset into the SQLite directory with `importDatabaseFromAssetAsync`
  (the code path behind `<SQLiteProvider assetSource>`), only when the asset's content hash differs from the one in
  `setting.catalog_asset_hash`, then opens it as a **separate read-only connection** (`PRAGMA query_only = ON`).
  The docs/08 text says "attached to `app.db`"; nothing in phase 1 needs a cross-database join (items store snapshots),
  so a second connection is simpler and keeps the catalog replaceable.

Trade-off: not committing the binary keeps git history small (every catalog version would add 6 MB forever) and
keeps the data reproducible from its sources, at the price of one extra build step and a first build that needs
network access (or a warm `catalog-build/downloads/`).
